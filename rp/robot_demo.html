The demonstration

The robot driving is the setup.
The failure is the point.

Anyone can film a robot crossing a room. Five minutes that show a fault appearing, being detected, being explained from evidence, and being recovered from — that is nearly unfakeable, which is exactly why it works.

The operations layer earns its place by answering three questions and nothing else: where is the robot, how is the mission going, and why did it stop. Everything shown here is derived from structured telemetry the robot already publishes.

It is advisory. It cannot command velocity, cannot bypass the navigation stack, cannot participate in a safety decision. If any model summarises a failure, it reads structured diagnostic events and issues no commands. That boundary is a stated design decision, and the demo says so out loud.

Deliberately unimpressive

One service, one database, one page. No orchestration, no message bus, no twin. Spending the demo on infrastructure would prove the thing nobody doubts.

03 — Failure injection catalogue

Every fault measured on the same five fields.

Detection latency, time to safe state, recovery time, mission impact, evidence trail. Measuring identically is what makes the results comparable — and makes the reports largely write themselves. Three become full investigations; the rest are logged.

Transport loss
Unplug or kill the serial device → interface watchdog trips, motors commanded to zero within a defined interval, controller enters error state
Network loss mid-mission
Disable the access point → continue autonomously or halt by policy; telemetry backlog handled; no duplicated mission on reconnect
Encoder channel disconnect
Unplug one channel → implausible wheel velocity detected, latched fault, motors disabled
IMU bias
Inject an offset in the driver → estimator yaw drift observable; measure drift rate and localisation error growth
Stale transform
Delay or stop a transform publisher → navigation transform timeout, controlled stop rather than acting on a stale frame
Node crash
Kill the controller manager or a navigation node → lifecycle handling, measured time to safe state, no uncontrolled motion
Localisation loss
Occlude the LiDAR or displace the robot → divergence detected, recovery attempted, failure reported rather than a confident wrong pose
Command timeout
Stop publishing velocity commands → firmware watchdog stops motors within the specified interval, independently of ROS 2
Frame corruption
Inject bad checksums → frames rejected, error counters increment, no misinterpreted command
Battery sag
Run to low charge → warning threshold, mission abort, safe park before cut-off
Motor overload
Drive into a fixed obstacle → wheels slip before the gearbox limit; I²t accumulator trips and latches

04 — Declared operating domain

Written before the robot first moves under power.

A 10 kg machine at 0.5 m/s in shared space is not a toy. This page is the cheapest professional marker available, and it is the first thing a mechanical or safety engineer looks for.

Environment
Indoor, level, dry hard flooring. No outdoor use, no ramps beyond 3°, no wet floors.
Exclusions
No operation within 2 m of stairs, loading edges, glass walls or unprotected drops.
Test protocol
Cordoned area, a designated observer present, bag recording started before power-on.
First power-on
Robot on blocks, wheels clear of the floor.
Roles
The observer holds the e-stop, may stop the test, and is not the person operating the software.
Pre-power checklist
Fuse fitted · battery in range · e-stop tested with software running · wheels clear · cordon in place · recording on.
After an incident
Stop testing. Preserve the bag. Write the log entry before changing anything.

Stated limitations

  • Navigation obstacle avoidance is not a safety function. It is best-effort behaviour from a single sensing plane.
  • A planar scan cannot see table edges, low obstacles, cables, overhangs or downward steps.
  • No rated safety scanner, no safety controller, no performance level. ISO 3691-4 and ISO 13849 are named to mark what a production system requires and this prototype does not have.
  • Battery charged outside the chassis, on a non-flammable surface, never unattended overnight.

05 — What it should leave behind

One conclusion, hard to argue with.

Not he learned ROS 2 and built a robot. Instead: this person derived the requirements, sized the drivetrain from a calculation, drew the real-time boundary in the right place, made safety independent of software, measured the failures instead of hiding them, and documented it so the next variant is cheap.

That is a robotics software architect describing a platform — which is the whole reason the project is shaped this way, and the reason the cloud layer stayed one page.
